# Browser validation audit — issue #103

Diagnostic/design deliverable, October 24, 2026 Pacific. Owner acceptance and any implementation/merge remain separate. No workflow, application, credential, service, schema or production change is made by this audit.

## Conclusion

**The primary PR browser path is already independent of Vercel.** Keep GitHub Actions, local Next.js and isolated PGlite/transport fixtures. The Sprint #91 hosted-preview failures did not prevent that suite from running: all four final feature heads have successful Core checks. Do not build another primary browser pipeline or provision staging to solve an access problem in the separate deployed checks.

The demonstrated gaps are missing CI artifact upload, unversioned hosted smoke procedures and limited runtime headroom. A build/HTTP success and an isolated browser pass are distinct from an executed deployed customer journey. Sprint #91 still needs the latter; this audit cannot waive it.

## Triggers, artifacts, coverage and repeatability

- Core runs on `pull_request` and pushes to main plus the three named legacy foundation/core/onboarding branches in the workflow. A feature push outside that list needs an open PR for Core to run. No `pull_request_target`, workflow dispatch, hosted-smoke trigger or deployment dependency is configured.
- The workflow declares `contents: read` and no service secrets, privileged environment, OIDC write permission or deployment credentials. Fork-code execution still uses dependency installation and test code; keep secrets absent. Repository Actions approval policy, branch protection/rulesets and whether Core is technically required were **not established** by this audit. Governance requires exact-head Core evidence; that does not prove a branch rule exists.
- Playwright retains traces on failure; tests explicitly save many screenshots under test-results. No workflow upload step, explicit HTML/JSON reporter, retention policy or video setting is present. A failed hosted runner loses those local files unless separately recovered. Empty artifacts on the diagnostic failure corroborate the gap. CLI logs remain useful but do not replace traces/screenshots.
- There is one worker and fixed ports 3100/3290. Gateway tests close the server/database in finally blocks; SQL fixtures use fresh in-memory databases. This avoids a shared hosted tenant and eliminates live-service cleanup from the primary suite. It also explains why increasing workers blindly would introduce port/state conflicts. Interrupted runs can leave workstation processes; the CI runner is ephemeral. No workflow concurrency/cancellation group or configured Playwright retry count exists.
- Chromium desktop and a 390px viewport run the full browser files. Firefox/WebKit projects match onboarding, storefront and checkout files, not every test file. Some onboarding branches return early on critical engines. #66's four-engine focused local run uses a temporary config; it must not be represented as full four-engine tracking coverage in checked-in CI.
- The tests assert roles/names, focus/containment/return, selected/current states, contrast and responsive bounds. These are accessibility regressions, not a scanner, manual screen-reader test, physical touch, physical Safari/iOS, or WCAG certification. [SUPPORTED-ENVIRONMENTS.md](SUPPORTED-ENVIRONMENTS.md) retains the owner-approved physical/real-AT deferral.
- Observed browser summaries range 13.0–18.8m; install, lint, SQL and build add time before them. These samples are not percentiles or an SLA. A 25-minute job can have little headroom; successful runs do not establish repeatability across runner load. No new timing benchmark or test rerun was necessary to diagnose the workflow. Blind retries would multiply usage and hide causes.

## Hosted-preview incident: facts and open questions

The earlier missing-variable Vercel build failure was real: branch-only connection variables did not cover new Sprint #91 branches. The owner separately approved only the two development public connection variables for general Preview; [PR #102](https://github.com/BravoKelo/Talix/pull/102) documents that correction. Existing branch overrides, Development/Production separation, email flags, guard and deployment protection were preserved. This audit makes no additional configuration change.

All four final feature heads subsequently reached READY and protected connector HTTP requests returned 200. Direct browser navigation, including the connector's temporary share link, redirected to Vercel SSO/login during the resumed attempt. This establishes an access-path discrepancy, **not** a diagnosed application failure, proof that protection must be disabled, or proof that owner sign-in is the only solution. The precise cause remains unverified. No disposable business was created in that attempt. Exact deployment URLs and live test state belong in [#97](https://github.com/BravoKelo/Talix/issues/97).

The Next.js guard in [src/lib/deployment-config.ts](../src/lib/deployment-config.ts) rejects missing public connection configuration when VERCEL_ENV identifies Preview or Production; [next.config.ts](../next.config.ts) invokes it. Local CI intentionally has its separate fixture environment; [tests/deployment-config.test.ts](../tests/deployment-config.test.ts) covers guard behavior. Keep this distinction and guard intact. Do not disguise a real hosted deployment as local to make it build.

## Minimal phased plan and acceptance criteria

This is a proposal, not authorization to edit code/workflows or provision resources.

1. **Now: documentation/evidence only (this issue).** Owner: current implementer; owner accepts the audit. Deliver this inventory, exact CI/hosted distinction and a separate Sprint #91 evidence handoff. Acceptance: references resolve, current/unverified states are explicit, no credential values, no executable/configuration changes. Existing primary PR independence meets the core requirement today.
2. **Proposed small CI evidence change.** Owner: implementer after bounded approval; retain the existing Core job/check and PR triggers. Add a named machine-readable/browser report and failure screenshots/traces uploaded even when tests fail (subject to cancellation/timeouts), with a proposed seven-day retention and documented redaction/fixture-only rules. Keep `contents: read`, no secrets, no new test database. Confirm a deliberate isolated failure yields downloadable diagnostics and a failed check; fix the deliberate failure before final review. Measure complete run duration from Actions rather than increasing timeouts/retries by assumption. Do not deliberately fail a production/live check.
3. **Proposed versioned operator smoke procedure/runner.** Owner: implementer, with service operator owning fixture cleanup; owner approves any persistent access/fixture decision first. Trigger only for trusted, explicitly selected exact PR head after primary Core succeeds and a matching deployment is READY. Vercel protection and application Auth are separate preflights. Prefer an existing same-project authenticated CLI/OIDC path or supported temporary access method; scope headers/cookies to the precise deployment origin and never print/store them in reports. Verify access with one bounded read before browser setup; on failure capture sanitized redirect/status and stop that flow. Do not redeploy an unchanged READY application to fix authentication. A CLI or access failure needs diagnosis, not recurring polling or an owner login request by default.
4. **After bounded approval, smoke acceptance.** Exact deployment/commit/project and development-only service identity verified. Disposable named fixture tenant/account only, no existing client writes. Complete real sign-in/session, affected owner save/publication and customer view, plus simulated checkout/tracking when those paths changed; use existing application APIs/permissions, no RLS bypass. Record browser/version/viewport/input, response failures, application versus provider errors, screenshots and individual results. Keep tokens, private tracking links and customer identifiers out of public artifacts. A fixture manifest and finally/teardown must identify exact IDs, verify cleanup counts and report retained fixtures on failure; never broad-delete by approximate name. Cleanup authority/credential transport must be approved before live writes. No mail, external payment or production side effects. READY/HTTP-only checks must be labeled accordingly.
5. **Only if measurements justify it:** propose splitting slow independent suites/jobs. Existing fixed-port/shared gateway behavior must be isolated per job first; preserve critical engine assertions. Estimate additional runner minutes and compare the existing 13–19m browser baseline. No extra dependency, worker count, timeout, retry policy or staging provision is approved here. A future production-build localhost browser smoke can use the existing `build`/`start` commands, but assess fixture/server route fidelity before replacing the existing dev-server suite.

Failure triage: classify checkout/install/build, local server/gateway startup, deterministic browser assertion, provider/browser access, actual application/service response, or fixture cleanup. Save the first useful failure evidence; retain required guards and assertions. Retry only after a concrete correction or identified transient condition, with at most one confirmation run for the same unchanged hypothesis; a repeated cause returns to diagnosis. Record elapsed run/step timing, not frequent unchanged progress polls. Hosted access failure leaves primary Core usable, but it does not waive applicable deployed acceptance.

Required review evidence remains Core/validate on the final reviewed revision plus affected deployed results under T02/T04/W02/D04. If formal branch protection is desired, first inventory current rules, then obtain a separate decision about required checks and bypass/merge permissions. Do not label the proposed artifact or hosted check technically required before it exists.
