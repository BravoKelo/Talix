# SaaS security and reliability

Classification and exception handling: [standards index](README.md). Current enforcement is PostgreSQL RLS/grants and checked RPCs, not a new application service framework.

| ID / level | Rule, purpose and applicability                                                                                                                                                                                                                                  | Enforcement                                                                                                                                            |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| S01 L1     | Every tenant resource must have an explicit client/subscription/location ownership path. Verify authorization for the actual resource, including Storage paths and cross-resource references. Tenant IDs supplied by a client never establish authority.         | RLS/grant/RPC review plus cross-tenant and cross-location denial tests; database constraints where applicable.                                         |
| S02 L1     | Treat requests as untrusted at each privilege boundary. Verify identity and effective permission server-side/database-side; UI hiding is usability only. Preserve protected Owner and separate Talix staff authority.                                            | Anonymous, outsider, employee, delegated-manager, Owner, admin and revoked-access cases as relevant.                                                   |
| S03 L1     | Least privilege and defense in depth: explicit grants, constrained definer functions with fixed search paths, safe public whitelists, and minimal credential scopes. Default new private operations to denied access.                                            | Migration/security review, denial tests and live advisors after approved DDL; assess intentional findings rather than suppress them.                   |
| S04 L1     | Secrets stay out of source, browser bundles, logs and artifacts. Public publishable keys are distinct from privileged credentials. Never log credentials, session values, private tracking tokens or unnecessary customer contacts.                              | Diff/artifact review and existing access controls; dedicated secret scanning is not established by this documentation.                                 |
| S05 L1     | Validate supported URLs/files/structured inputs, use parameterized SQL and safe rendering, and restrict public output to approved fields. Preserve private tracking no-index/no-referrer handling.                                                               | Boundary tests for malformed input, unauthorized fields and token leakage.                                                                             |
| S06 L1     | Retain database integrity: enforce ownership references, constraints and atomic operations. Compute authoritative prices in integer cents, not from browser totals. Preserve purchase/order snapshots.                                                           | Actual SQL tests for invalid references, totals, historical preservation and partial-write failure.                                                    |
| S07 L1     | Applied migrations are immutable. Prepare additive compatible changes where possible; destructive changes require explicit approval, compatibility/data-recovery review and a concrete execution plan. Do not replay old migrations to fix branch compatibility. | Review exact SQL, explicit environment/execution authorization, migration history and post-change verification.                                        |
| S08 L1     | Retryable writes require appropriate idempotency, transaction locking and stale-state checks. Reject reused keys with changed payloads; distinguish failure from unknown response.                                                                               | Duplicate/replay/price/version tests; use real concurrent-session tests when concurrency behavior is the changed risk and report isolated-test limits. |
| S09 L2     | Contracts document request/response shapes, authority, errors, retry semantics, compatibility and current consumers. Preserve stable interfaces or explicitly version/migrate consumers.                                                                         | Type/SQL/browser contract checks and migration/consumer review.                                                                                        |
| S10 L2     | Prefer stateless request processing when appropriate. Keep durable correctness in authoritative storage; do not use process memory as an order/payment authority. UI-only carts may retain their accepted in-memory behavior.                                    | Review lifecycle, restart and multi-instance assumptions.                                                                                              |
| S11 L1     | When asynchronous processing is approved, define duplicate delivery, retry limits/backoff, idempotency, failure visibility and recovery before relying on it. Do not claim queues or background workers exist today.                                             | Failure/recovery tests for the actual introduced mechanism; no requirement to add a queue now.                                                         |
| S12 L2     | Provide structured, privacy-safe diagnostics for material operations: operation, safe correlation identifier, outcome and useful error classification. Distinguish unavailable/loading/empty/error states and offer bounded retries.                             | Review failure behavior and relevant tests; centralized observability is a documented gap.                                                             |
| S13 L1     | Operational changes require environment scope, compatibility checks and a feasible recovery plan. Consider forward fixes, backups/restores and data effects; code rollback does not undo migrations or external actions.                                         | Approved execution record with actual outcomes; never improvise destructive rollback.                                                                  |
| S14 L3     | Measure before optimizing. Bound expensive queries/payloads, inspect relevant indexes and render/network costs, and set performance targets for demonstrated journeys. Avoid speculative scale infrastructure.                                                   | Query plans, timings or profiling appropriate to the observed bottleneck; no invented SLA.                                                             |
