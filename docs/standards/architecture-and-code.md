# Architecture and code quality

Classification and exception handling: [standards index](README.md). Existing conventions are evidence; inspect neighboring implementation before choosing a new pattern.

| ID / level | Rule, purpose and applicability                                                                                                                                                                                                                                                                                                      | Enforcement                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| A01 L2     | Separate rendering, orchestration, domain validation and persistence responsibilities so changes remain understandable. Apply when adding/changing features; do not require a layered rewrite of every component.                                                                                                                    | Review responsibility and side-effect boundaries; focused tests.                                |
| A02 L2     | Give each function/component/module one coherent responsibility. Split when independent behavior, state or dependencies make it hard to reason about. Prefer small focused units; line counts are signals, not universal limits.                                                                                                     | Diff review and targeted behavior tests; no file-length tool gate exists.                       |
| A03 L3     | DRY: reuse genuinely shared behavior after examining existing components/services; do not unify coincidentally similar domain rules.                                                                                                                                                                                                 | Review duplicated behavior and coupling costs.                                                  |
| A04 L3     | KISS and YAGNI: implement the demonstrated approved requirement with the simplest adequate design. Avoid speculative plugins, layers and extension registries.                                                                                                                                                                       | Explain material abstractions and demonstrated consumers in PR.                                 |
| A05 L2     | Dependency inversion: keep business decisions independent of replaceable delivery/provider details where a real boundary exists. Use explicit inputs and narrow interfaces; do not mandate dependency-injection frameworks.                                                                                                          | Inspect imports and contracts; replaceable-boundary tests when justified.                       |
| A06 L2     | Define module responsibilities, consumers and allowed dependencies when a module is introduced. Keep controlled interfaces, minimize deep imports and avoid circular dependencies.                                                                                                                                                   | Architecture/ADR review and import inspection; no automated dependency graph enforcement today. |
| A07 L3     | Use domain language and bounded contexts when actual business rules differ. Do not infer contexts from industry labels or introduce full DDD scaffolding without need.                                                                                                                                                               | Document meaningful ownership/terminology decisions.                                            |
| Q01 L2     | Write readable code with descriptive domain names; follow existing kebab-case file conventions, PascalCase React components/types and camelCase functions/values. Keep routes in src/app, UI in src/components, shared non-UI helpers/types in src/lib and migrations/tests in their established homes. A new layout needs evidence. | Neighboring-code/diff review; lint catches only configured subsets.                             |
| Q02 L2     | Preserve strict typing. Narrow unknown external data after runtime validation; avoid unexplained any, unsafe casts and non-null assertions. Model meaningful states explicitly.                                                                                                                                                      | npm run typecheck with strict enabled; review escape hatches.                                   |
| Q03 L1     | Validate untrusted input before privileged work, and again at the authoritative boundary. Reject invalid money, tenant references, transitions and incompatible selections before writes; preserve atomicity.                                                                                                                        | SQL/integration negative cases and boundary review.                                             |
| Q04 L2     | Handle expected errors explicitly, preserve diagnostic context safely and show actionable customer language. Do not swallow failures or report success after an unknown result.                                                                                                                                                      | Error/retry tests and review; no blanket catch-and-ignore.                                      |
| Q05 L2     | Explain non-obvious invariants, compatibility paths and unusual tradeoffs near the code or owning documentation; omit comments that merely restate syntax.                                                                                                                                                                           | Review whether a new maintainer can safely change behavior.                                     |
| Q06 L2     | Refactor incrementally with preserved behavior when needed for the approved change. Remove obsolete code only after checking consumers, compatibility and coverage. Do not mix unrelated cleanup with feature work.                                                                                                                  | Focused diff and relevant regression checks; protected changes remain separately approved.      |
| Q07 L2     | Reuse existing accessible dialogs, navigation, image handling and validation where suitable. Preserve focus, keyboard access, touch usability, staged Save/Cancel and responsive behavior when changing their consumers.                                                                                                             | Relevant browser tests and visual review; reuse is not forced when responsibilities differ.     |
