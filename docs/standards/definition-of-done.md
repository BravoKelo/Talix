# Engineering Definition of Done

Status: proposed for owner review, October 18, 2026 Pacific, as an owner-requested extension of PR #61. Documentation only; no code, service, migration, dependency, infrastructure, audit, issue-creation, deployment or merge authority. A working happy path alone is not “done.” This document applies the existing [governance](../../AGENTS.md), [classified standards](README.md) and [testing/workflow](testing-and-workflow.md); it does not replace owner acceptance, invent new automatic CI gates or authorize production release.

## D01 — Explicit applicability and approved outcomes (L1)

**Purpose/applicability:** Make completion assessable for every meaningful change. **Requirement:** Record approved scope/issue when authorized, exact reviewed head, expected outcomes and the applicable criteria below. Mark each criterion Applicable (with evidence/pass/fail), Not Applicable (with reason), or Deferred (with impact/owner/date/approval and closure plan). Unexecuted/unavailable checks are not passing evidence. Deferred mandatory work cannot be silently waived or called complete. **Verification:** Review the completed evidence record and resulting full diff. **Timing:** Scope planning and before acceptance. **Limits:** Not every criterion requires a new tool/test for every change; documentation-only work uses documentation checks. Issue creation is not authorized by this standards task.

## D02 — Required verification and quality review (L1)

**Purpose/applicability:** Verify relevant behavior, boundaries and regressions. **Requirement:** Complete suitable available tests/manual checks, investigate failures and complete required exact-head CI/review under T01–T04. Include affected security/tenant/transaction negative cases, supported responsive/input/accessibility evidence and relevant integration/failure/recovery/performance checks. Review the complete final diff, not only a passing primary test. **Verification:** Actual commands/environments/results, manual steps and limits; distinguish historic, mocked, emulated, physical, sandbox and live evidence. **Timing:** Before acceptance/merge of affected work. **Limits:** No requirement to install all suggested tooling, replay migrations or run dangerous checks. Safe validation authority and protected approvals remain mandatory; an unavailable required check needs explicit disposition under existing rules.

## D03 — Documentation and operational handoff (L2)

**Purpose/applicability:** Make accepted work maintainable and recoverable. **Requirement:** Update owning architecture/ADR, product/contract/configuration, current-state and operational docs where affected, without duplicating authority or rewriting approval history. Record relevant safe diagnostics, deployment/schema/provider compatibility, recovery limits, unresolved risks, owners and next action. **Verification:** Source/decision consistency, relative links and a readable handoff with actual implemented versus planned state. **Timing:** Before affected completion and after authorized integration as applicable. **Limits:** No new ADR for trivial choices, full runbook for prose changes or unrelated cleanup. Protected architecture approval still follows W04.

## D04 — Acceptance, deferrals and operational authorization (L1)

**Purpose/applicability:** Prevent test success from becoming unapproved scope or release. **Requirement:** Owner acceptance must identify exact reviewed commit and material boundaries, with applicable L1 violations resolved before approval/merge. A mandatory deferral needs explicit owner decision under existing governance; recording it is not a waiver or a claim of complete compliance. Any replacement of a protected requirement needs its documented governing decision and cannot weaken tenant isolation/authority. L2 departures need explicit technical justification. Preserve separate implementation, schema/migration, infrastructure/security, merge and deployment approvals. **Verification:** Acceptance/exception record, exact-head checks and actual execution permissions. **Timing:** Before acceptance, merge or operational activation. **Limits:** No feature may be labeled fully complete while an applicable mandatory criterion remains unresolved; report partial/blocked scope. Successful CI, an issue closure or accepted documentation is not deployment authorization.

## Completion evidence checklist

| Area                          | Applicable completion evidence / owning standards                                                                                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Functional correctness        | Approved requirements/outcomes, error/edge cases and expected failure recovery demonstrated; Q03/Q04/T01.                                                                                               |
| Architecture                  | Existing domain/dependency/industry boundaries and ADRs preserved; justified abstraction only; A01–A07/P01/P02/P08.                                                                                     |
| Security/privacy              | Actual identity/resource authorization, tenant isolation, input validation, safe sensitive-data handling and applicable negative tests; S01–S06/B01/B07.                                                |
| Entitlements                  | Actual restricted features enforce centralized industry/tier eligibility at authoritative entry points and transitions; P03/B05/I67. Absence of a hypothetical engine is not a current feature failure. |
| Accessibility                 | Applicable AC criteria and complete affected workflows, keyboard/screen-reader/focus/contrast/form checks and documented limits; X44/AC01–AC16.                                                         |
| Cross-platform                | Approved viewport/orientation/browser/input scope tested and evidence limits explicit; X41–X54.                                                                                                         |
| Integrations                  | Contract/auth/tenant/privacy, timeout/retry/idempotency/sync/webhook/quota behavior and provider failures tested when applicable; I56–I70.                                                              |
| Regression and validation     | Suitable automated/manual coverage, actual results and required exact-head CI; independent concurrency/service fidelity where relevant, T01–T04.                                                        |
| Performance/capacity          | No unacceptable regression against approved method/targets; query/payload/render/expensive workload review; S14/X47/O07/O08.                                                                            |
| Documentation                 | Owning decisions/contracts/configuration/handoff updated, links checked and implemented versus future claims accurate; W05/D03.                                                                         |
| Operations/recovery           | Critical errors visible safely, failure effects understood, environment/schema/release compatibility and feasible recovery, verified backup strategy before production-critical reliance; O01–O06.      |
| Tenant/subscription lifecycle | Safe provisioning/retry/defaults, ownership/purchase preservation, data retention/export/closure and subscription transition impacts where affected; B01–B08.                                           |
| Review and approvals          | Full diff reviewed, mandatory criteria resolved, justified L2 exceptions, exact-head checks and explicit owner acceptance/operational boundaries; W01/W02/W04/D04.                                      |

For each applicable row, include relevant IDs, evidence link/command/manual record, environment/date, result and limitations. For a deferral add user/security/operational impact, reason, mitigation, responsible owner, priority, review/target date, approval record and closure evidence. Not Applicable needs a concrete reason tied to scope. Reassess after material edits; old CI or prior manual acceptance cannot silently certify a different application head. No exception becomes permanent through silence.

Documentation-only PRs can satisfy this definition with source/governance consistency, link/ID checks, preserved instructions, scope/diff review and required review/CI evidence. Do not install dependencies, mutate live data or execute migrations merely to “complete” a checklist. These standards introduce manual review requirements, not new enforcement infrastructure.
